# BUG-001 — Admin pages render without breadcrumbs or admin sidebar

**Ticket:** MD-2189  
**Reported:** 2026-05-08  
**Status:** Fixed (same session)  
**Severity:** Medium — pages function correctly but lack admin chrome  

---

## Screenshot

`migrate.php` rendered via `https://lsuce-dvdcastro.ngrok.dev/blocks/backadel/migrate.php` — content is correct but the page shows the Snap theme header with no admin breadcrumb trail and no left admin navigation sidebar.

---

## Root cause

All six backadel admin pages (`migrate.php`, `restore.php`, `catalogue.php`, `results.php`, `failed.php`, `delete.php`) performed manual page setup:

```php
require_login();
$context = context_system::instance();
require_capability('block/backadel:...', $context);

$PAGE->set_context($context);
$PAGE->set_url($pageurl);
$PAGE->set_title(...);
$PAGE->set_heading(...);
```

This produces a valid, capability-protected page, **but** it never calls `admin_externalpage_setup()` — the Moodle core function that:

1. Sets `$PAGE->set_pagelayout('admin')` — switches the theme to admin chrome
2. Builds the breadcrumb trail from the admin tree node registered in `settings.php`
3. Locates and activates the correct node in the admin sidebar

Without `admin_externalpage_setup()`, Moodle falls back to the current theme's default layout (`'base'` or `'standard'` in Snap), which renders the regular course header, no admin sidebar, and no breadcrumb path showing where the page sits in Site administration.

The pages were registered as `admin_externalpage` entries in `settings.php`, but registration alone is not sufficient — each page must also call `admin_externalpage_setup('<internal_name>')` to opt into admin chrome at render time.

---

## Fix applied

For each page, replace the manual setup block with a single `admin_externalpage_setup()` call, then keep the plugin-specific `require_capability()` below it (admin_externalpage_setup calls `require_login()` and sets the system context internally, but does **not** enforce plugin capabilities).

The internal names match the `admin_externalpage` names registered in `blocks/backadel/settings.php`:

| File | Internal name |
|------|--------------|
| `migrate.php` | `block_backadel_migrate` |
| `restore.php` | `block_backadel_coursebackups` |
| `catalogue.php` | `block_backadel_catalogue` |
| `results.php` | `block_backadel_results` |
| `failed.php` | `block_backadel_failed` |
| `delete.php` | `block_backadel_delete` |

Pattern applied to every page:

```php
// Before (broken):
require_login();
$context = context_system::instance();
require_capability('block/backadel:managemigration', $context);
$PAGE->set_context($context);
$PAGE->set_url($pageurl);
$PAGE->set_title(get_string('migrate_pagetitle', 'block_backadel'));
$PAGE->set_heading(get_string('migrate_heading', 'block_backadel'));

// After (correct):
admin_externalpage_setup('block_backadel_migrate');
$context = context_system::instance();
require_capability('block/backadel:managemigration', $context);
```

`restore.php` has a URL with dynamic query params (`year`, `id`). These are passed via the `$extraurlparams` argument:

```php
admin_externalpage_setup('block_backadel_coursebackups', '', ['year' => $year, 'id' => $restorecourseid]);
```

## Q: Migration task queued but no visible change — is that expected?

**Yes, this is expected behaviour in the current environment.**

The catalogue table (`block_backadel_catalogue`) was pre-seeded with **51,385 rows** via fixture SQL inserts. The BACKUPDIR contains **104 fixture ZIP files**. When the adhoc migration task runs, it scans BACKUPDIR, parses each filename, and attempts to insert catalogue rows — but the dedup logic (`filepath_hash` uniqueness) causes all or most rows to be skipped as duplicates.

The count stays at 51,385 because there is nothing new to add: the fixture already covers the expected data set.

**To see a count increase:** add a new ZIP file to BACKUPDIR that does not match any existing `filepath_hash`, then queue another migration. Or truncate the catalogue table and re-run to watch it repopulate from the 104 fixture files.

## Q: Was the database seeded? Should we build a seed script?

**What is already seeded:**
- `block_backadel_catalogue` — 51,385 rows (fixture SQL, pre-populated)
- BACKUPDIR — 104 fixture ZIP files (fixture data, pre-populated)
- `block_backadel_courses`, `block_backadel_teachers` — seeded as part of fixture

**What is NOT seeded (empty):**
- `block_backadel_statuses` — no backup jobs have been queued or run
- `results.php` — will show empty table (no backup queue entries)
- `failed.php` — will show empty (no failures)
- `delete.php` — will show empty (no SUCCESS-status archives)

**To test results.php end-to-end**, a backup job must exist in `block_backadel_statuses`. This requires:
1. A Moodle course to exist
2. A POST to `results.php` (queue action) for that course
3. Cron to run the backup task (or a direct `php admin/cli/cron.php`)

**Recommended: build a seed script** at `tickets/MD-2189/seed/seed_statuses.php` that inserts rows directly into `block_backadel_statuses` with BACKUP, SUCCESS, and FAILED statuses so all three pages (`results.php`, `failed.php`, `delete.php`) display data without needing to run real backups. This is purely for local dev/QA testing.
