# Bug-003 — Course Backups Restore button routes to site course (SITEID)

**Date:** 2026-05-08  
**Discovered:** Live QA on https://lsuce-dvdcastro.ngrok.dev  
**Severity:** High — pressing Restore presents "Overwrite current course" targeting the site course (course id=1)

---

## Symptom

On the Course Backups admin page (`/blocks/backadel/restore.php`), clicking the **Restore** button for any catalogue entry lands the user on:

```
/blocks/simple_restore/restore.php?contextid=2&filename=<hash>&restore_to=0
```

with the page title **"Simple Restore: Overwrite current course"** and the confirmation message:

> You are about to **Overwrite current course**. Proceed?

The "current course" in this context is the **site course** (Moodle course id=1), because `restore.php` is accessed from the admin menu without a valid target course id.

---

## Root Cause

`blocks/backadel/restore.php` reads the target course id from an optional URL param:

```php
$restorecourseid = optional_param('id', SITEID, PARAM_INT);
```

When accessed from the admin navigation (no `id` param), `$restorecourseid = SITEID = 1`.

The Restore button then builds:

```php
$restoreurl = new moodle_url('/blocks/simple_restore/list.php', [
    'id'     => $restorecourseid,   // ← 1 (SITEID)
    'name'   => 'catalogue',
    'action' => 'choosefile',
    'fileid' => $row->id,
    'sesskey' => sesskey(),
]);
```

`simple_restore/list.php` receives `id=1`, evaluates `$archivemode = (1 == SITEID && get_config('simple_restore', 'is_archive_server'))`, and since `is_archive_server` is not set, proceeds with `context_course::instance(1)` — the site course context.

Because `action=choosefile`, `name=catalogue`, and `fileid` are all present, `list.php` bypasses the file-picker UI entirely and calls `prep_restore()` immediately, staging the file for restore and redirecting to the Simple Restore confirm page targeting **course id=1 (the site)**.

---

## What the Implementation Plan Says

`tickets/MD-2189/IMPLEMENTATION_PLAN.md` §3.4 defines the intended Restore button behaviour:

> **Restore** — Copy file to user draft area → redirect to  
> `/backup/restore.php?contextid=...&component=user&filearea=draft&itemid=...`

The plan explicitly specifies Moodle's **native** restore wizard, not Simple Restore with a pre-wired course target. Using the native path avoids the "which course?" ambiguity entirely — Moodle's restore wizard lets the admin choose to restore into a new course or an existing one during the wizard flow.

---

## Impact

- Any admin clicking Restore from the Course Backups admin page would be presented with a confirmation to **overwrite the site course** — catastrophic if confirmed.
- The Simple Restore path (`simple_restore/list.php`) was designed for teachers restoring **into their own course**; it is the wrong entry point for an admin-level catalogue browse.

---

## Proposed Fix

See the Opus agent plan (to be created alongside this bug file).

**Short version:**

1. In `restore.php`, replace the Simple Restore URL with a call that copies the catalogue file to a Moodle user draft area (via `file_storage`) and redirects to `/backup/restore.php?contextid=<system_or_chosen>&component=user&filearea=draft&itemid=<draftid>`.
2. Remove the `id` / `restorecourseid` dependency from the Restore button — the native restore wizard handles course selection.
3. Guard: if the resolved absolute path does not exist on disk, show an error instead of staging a restore.
